# clustering-rules · 聚类阈值的来源与反例

## 阈值由来

trip-design 的两个核心阈值：

| 阈值 | 值 | 含义 |
|------|-----|------|
| `SAME_LOC_M` | 500 m | 相邻两张照片 GPS 距离 < 500m → 视为同地点 |
| `NEW_LOC_M` | 2000 m | > 2 km → 视为新地点（强制开新组）|

500m–2km 是"灰区"，trip-design **保守地划入同组**——避免过度碎片化。

### 为什么 500m

500m 大约是**步行 5 分钟**（人步速 80m/min）。一个景点（公园、街区、神社）的合理活动半径就是这个量级。两张拍摄相隔 5 分钟、位移 < 500m 的照片，几乎不可能是"换了一个地点"。

举例：
- 「国際通り」一条商业街长约 1.6 km，从北端走到南端会触发 NEW_LOC_M（2 km）——这是正确的，南北两端体感是不同地点
- 「首里城公園」内的"守礼門 → 正殿 → 龍潭"互距 < 500m，全归一组——正确

### 为什么 2km

2km 大约是**短程驾车 5 分钟**（市区车速 30km/h）。位移 > 2km 一般意味着"主动换地方"（开车 / 公交 / 长距离步行）。

举例：
- 那覇市内从「国際通り」（26.214,127.681）到「首里城」（26.217,127.719）直线 4 km → 触发 NEW_LOC_M，正确
- 美ら海水族館（26.694,127.878）→ 古宇利島（26.705,128.013）13 km → 触发 NEW_LOC_M，正确

## 反例与权衡

### 反例 1：长距离散步

用户在京都"哲学之道" 2 km 慢走，每 100m 一张。当前阈值会**正确归一组**（任意两点 < 2km）。

### 反例 2：山顶 + 山脚

某些景点的"上山缆车口"和"山顶观景台"水平距离 < 1 km，但用户在两处分别停留 1 小时。当前阈值会**误归一组**（< 2km）。

**当前不处理**——开 30+ 分钟的时间间隙规则会让代码复杂、且对绝大多数用户造成更多误聚类。如果用户想拆，🛑 (b) 检查点会让 ta 手动说："Day 2 的 14:00-15:00 是山脚，15:30-17:00 是山顶"。

### 反例 3：开车经过

用户在高速上开车，每 5 km 拍一张窗外。当前阈值会**错误地把每张都开成新地点**。

**当前不处理**——这种场景本身不是 trip-design 的目标用户（"自驾途中拍窗外"不是日记，是行程记录）。

### 反例 4：无 GPS 串联

第 5 张照片有 GPS 在 A 地，第 6-9 张无 GPS（室内餐厅），第 10 张又有 GPS 在 B 地（5 km 外）。当前规则：6-9 继承 A 地。

**这是有意为之**：照片是按时间序的；6-9 时间紧贴 5 而非 10，吃饭地点更可能在 A 附近。如果 6-9 实际在 B 附近，🛑 (b) 检查点用户可手动调整。

## 封面照启发式

每地点 / 每天选「文件最大」作封面：

```python
cover = max(photos, key=lambda p: p.get("filesize") or 0)
```

**为什么**：
- 文件大 ≈ 信息量大（光线丰富、细节复杂、压缩比低）
- iPhone 抓拍的"差不多"两张里，更内容丰富的那张文件大约 30-50%
- 不需要 ML 也能 70-80% 选到合理代表

**反例**：
- 用户拍了一张 Live Photo 的 .heic（含运动数据，文件特别大），但内容是擦镜头时的废片 → 当封面会失败
- 文件大不等于美——当前 V1 接受这个 tradeoff

后续可加：人脸检测、构图启发式、用户手选——但 V1 的最大文件启发式已经够用。

## 一天的 cover_photo

`days[].cover_photo_id` 取**该天第一个地点**的封面照——理由是 hero 区视觉上需要"一眼对应这天"，第一个地点通常是早晨上路时的氛围照，最有"开篇"感。

## 阈值的可调性

阈值是模块顶部常量，不暴露给 CLI——避免用户被参数迷惑。如果未来发现某类用户（自驾游 / 徒步党 / 城市散步党）需要不同默认，再考虑出预设：

```python
PRESETS = {
    "city": (200, 1000),     # 步行密集
    "drive": (5000, 50000),  # 自驾长途
    "default": (500, 2000),
}
```

V1 不做。
